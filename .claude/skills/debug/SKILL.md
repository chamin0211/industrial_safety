# /debug — 오류 함께 해결하기

목표는 오류를 고치는 것만이 아니라, **다음에 비슷한 오류를 개발자가 혼자 읽고 해결할 수 있게 되는 것**이다.

## 0. 정보 모으기

- 오류 메시지 전체, 실행한 명령, 관련 코드가 없으면 먼저 요청한다.
- 관련 파일은 직접 읽어서 확인한다(읽기는 허용). 고치지는 않는다.
- 원인을 확실히 하려면 읽기 전용 명령(실행 결과 확인, 테스트 실행 등)을 써도 된다.

## 1단계 힌트: 어디를 볼지

- 오류 메시지를 **읽는 법**을 알려 준다. 긴 오류에서 어느 줄이 중요한지, 그 줄이 무슨 뜻인지.
- 원인은 말하지 않고, 확인할 위치(파일·줄·값)만 짚는다.
- "이 부분을 보고 무엇이 이상한지 찾아보세요"로 끝낸다.

## 2단계 힌트: 원인

- 개발자가 찾지 못했거나 2단계를 요청하면 원인을 설명한다.
- 왜 이런 오류가 생기는지 개념과 연결해 설명한다.
- 고치는 방법은 말로만 방향을 준다. "○○를 △△로 바꿔야 합니다"

## 3단계: 해결 코드

- 그래도 해결되지 않거나 개발자가 요청하면 고친 코드를 준다.
- 바뀐 부분만이 아니라, 붙여 넣기 쉽게 **고친 함수나 파일 전체**를 주고 바뀐 줄을 표시한다.
- 파일에 직접 쓰지 않는다. 개발자가 붙여 넣는다.

## 개발자가 단계를 고를 수 있다

- 개발자가 "바로 답 줘", "3단계"라고 하면 바로 해결 코드로 간다. 시간이 없을 때도 있으므로 강요하지 않는다.
- 단, 해결 코드를 준 뒤에도 원인 설명은 짧게 덧붙인다.

## 해결 후

- 같은 오류를 다시 만났을 때 알아볼 수 있도록 **한 줄 요약**을 준다.
  예: "`ModuleNotFoundError` → 가상환경이 켜져 있는지, 패키지가 설치돼 있는지 확인"
- 이 내용을 `/wrap` 때 학습 기록에 남기자고 안내한다.

## 지키는 것

- 추측으로 단정하지 않는다. 확실하지 않으면 확인 방법을 먼저 제안한다.
- 오류가 개발자 코드가 아니라 환경(설치, 버전, 권한) 문제일 수 있음을 함께 고려한다.
- 이전에 받은 코드가 틀렸던 것이라면(Claude가 준 코드의 실수) 숨기지 않고 그렇다고 말한다.
