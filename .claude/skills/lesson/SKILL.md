# /lesson — 작업 시작

개발자가 이해하며 직접 작성할 수 있도록 한 작업을 안내한다. 코드는 **파일에 쓰지 않고 대화로만** 보낸다(AGENTS.md).

## 0. 준비 (개발자에게 보이지 않게 확인)

1. `docs/progress.md`에서 지금 위치와 다음 할 일을 확인한다. 인자가 있으면(예: `/lesson 6`) 그 작업을 대상으로 한다.
2. `docs/PLAN.md` 7장에서 해당 작업의 **만들 것·배울 것·완료 기준**을 확인한다.
3. `docs/learning-log.md`의 "아직 헷갈리는 개념"을 확인한다. 이번 작업과 관련 있으면 설명할 때 짚는다.
4. 이미 작성된 관련 코드가 있으면 읽어서 현재 상태를 파악한다.

## 1. 작업 소개 (짧게)

- 이번 작업이 무엇이고, 전체 흐름에서 어디에 해당하는지 한두 문장
- 끝나면 무엇이 되는지 (완료 기준)
- 이번에 이해할 **핵심 개념 2~3개** 이름만 먼저 알려 준다

## 2. 개념 설명

- 핵심 개념을 하나씩 쉬운 말과 비유로 설명한다.
- 지난 학습 기록에 헷갈린다고 적힌 개념이 나오면 "지난번에 헷갈린다고 하셨던 ○○"라고 연결한다.
- 길어지면 여기서 멈추고 이해했는지 묻는다.

## 3. 코드 전달

- **완성된 전체 코드**를 준다. 빈칸 채우기 방식은 쓰지 않는다(D9).
- 한 번에 **파일 하나** 단위로 준다. 파일이 여러 개면 순서를 알려 주고 하나씩 진행한다.
- 각 파일마다:
  - 파일 경로 (어디에 만들지)
  - 전체 코드
  - **블록별 설명**: 이 부분이 무엇을 하고 왜 이렇게 쓰는지
  - 처음 보는 문법·라이브러리는 따로 짚는다
- 현업에서 흔히 쓰는 방식과 다르게 짰다면 그 이유를 말한다.

## 4. 실행·확인 안내

- 실행할 명령과 각 명령의 의미
- 기대 결과 (어떤 출력이 나오면 성공인지)
- 오류가 나면 결과를 그대로 붙여 달라고 안내한다 → `/debug`

## 5. 마무리 안내

- 코드를 다 작성하고 실행이 되면 `/review`로 리뷰, 이후 이해 확인으로 작업을 완료한다고 알려 준다.
- 한 작업이 길면 오늘 어디까지 할지 개발자와 정하고, 끝날 때 `/wrap`을 안내한다.

## 지키는 것

- 앱 코드는 Write/Edit/셸로 파일에 쓰지 않는다 (훅이 막음).
- 개발자가 이해하지 못했다고 하면 같은 설명을 반복하지 말고 더 쉽게 다시 설명한다.
- 한 번에 많은 양을 보여 주지 않는다. 개념 → 코드 → 실행을 단계마다 확인받으며 진행한다.
- 준비 단계처럼 앱 코드가 아닌 작업(공부, 데이터 확인)도 같은 순서를 따른다. 이때 "코드"는 데이터 확인용 짧은 스크립트이고, 개발자가 직접 실행한다.
