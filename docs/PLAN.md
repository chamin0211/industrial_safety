| D12 | 실행 구성: **Docker Compose** 한 번에 설치. 로컬 LLM은 개발 PC에서 **Ollama**(7~8B), 품질 측정은 Colab에서 **vLLM**(목표 사양 모델). 계정 연동 테스트는 **Keycloak + OpenLDAP**. **Redis·Kubernetes는 쓰지 않음** | 고객사 한 곳, 서버 한두 대 규모라 단순한 구성이 설치·관리에 유리. LLM 학습 없이 RAG로 정확성 확보. 검색(R) 품질은 PC에서, 생성(G) 품질은 큰 모델로 측정. 모델은 설정으로 교체(코드 수정 없음) |

| D14 | 하네스는 **AGENTS.md 계층 구조**(상시 규칙·실행 계획·스킬·evals·CHECKLIST)에 학습형용 훅·학습 기록을 더해 최소 구성으로 시작 (9장) | AGENTS.md는 여러 AI 코딩 도구의 공통 표준이라 현업 이식성이 높음. 작업 절차 스킬은 실제로 해 본 뒤 만든다 |

## 1. 프로젝트 정의

**한 줄 정의:** 화학물질·가스 취급 작업 전에, 유사 사고 사례·법령·KOSHA 지침·물질 유해성을 찾아 **출처가 달린 점검표 초안**을 만들어 주는 **기업용 설치형 AI 솔루션**.

**진행 방식:** 대상 고객 프로필과 요구사항 명세를 먼저 작성하고, 이를 기준으로 구축·검수한다. 실제 기업 구축 프로젝트와 같은 흐름(요구사항 → 설계 → 구축 → 설치 → 검수 → 운영 문서)을 따른다.

**계기가 된 사례:** 2026년 6월 SK하이닉스 청주공장 가스룸 화재. 한 달 사이 두 차례 발생했고, 두 번째는 가스 캐비닛에서 불소와 질소를 혼합하던 중 일어났다. 이 작업은 시연 시나리오 중 하나로 사용한다.

## 2. 사용자와 핵심 흐름

### 사용자 역할 (확정: D3)

| 역할 | 하는 일 |
|---|---|
| 시스템 관리자 (고객 기업 IT 담당) | 프로그램 관리: 설치·업데이트, 계정 발급·역할 지정, 백업 |
| 안전팀 관리자 | 사내 문서·작업 템플릿 관리, 현장 관리자가 제출한 점검 이력 확인 |
| 현장 관리자 | 로그인 → 작업 전 유의사항(점검표) 확인 → 항목별 체크·메모 → 완료 제출 |

### 시스템 흐름

| 흐름 | 누가 | 내용 |
|---|---|---|
| ① 지식 준비 | 시스템 (설치·갱신 시) | 공공데이터(사례·법령·지침·MSDS) 수집 → 정제 → 청크 분할 → 임베딩 → DB 저장 |
| ② 관리 준비 | 시스템 관리자, 안전팀 관리자 | 설치, 사내 계정 서버 연결·그룹→역할 매핑 / 사내 문서 업로드·열람 범위 지정 → ①과 같은 처리 |
| ③ 작업 전 점검 | 현장 관리자 | 아래 "핵심 흐름" |
| ④ 이력 확인 | 안전팀 관리자 | 제출된 점검 이력 조회 (작업·날짜·제출자·체크·메모·미체크 항목) |
| ⑤ 품질 평가 | 개발자 | 평가 질문 세트로 채점 → 기록 → 개선 전후 비교 |

### 핵심 흐름 (③ 작업 전 점검)

1. **현장 관리자** 로그인 (사내 계정)
2. 작업 입력: 작업 내용, 취급 물질. **검색은 사용자가 하지 않고 시스템이 자동으로 한다.**
3. 에이전트 조사: 물질 파악 → MSDS 조회 → 유사 사고 사례 → KOSHA 지침 → 법령 조문 → 사내 문서(열람 권한 내)
4. LLM이 점검표 초안 작성: 모든 항목에 출처를 붙인다
5. 근거 검증: 항목마다 ① 인용 출처가 3에서 실제로 찾은 문서인지, ② 출처 내용이 항목을 뒷받침하는지 확인. 통과하지 못한 항목은 삭제하고, 근거를 찾지 못한 부분은 "확인되지 않음"으로 표시
6. 화면 표시: 점검표 + 항목별 출처 원문
7. 현장 체크: 항목별 확인·메모 → 완료 제출
8. **안전팀 관리자**: 제출 이력 확인 (④)

### 근거 규칙

- LLM의 답을 그대로 믿지 않는다. 생성 단계(4)와 **별도로** 검증 단계(5)를 둔다. 인용 출처가 실제로 있는지는 코드로 확인하고, 내용이 뒷받침하는지는 별도 판정으로 확인한다.
- 내용 판정은 모델이 하므로 100% 정확할 수 없다. 그래서 평가 세트로 근거 일치율을 측정하고(목표 ≥ 90%), 화면에는 출처 원문을 항상 함께 보여 준다.
- "확인되지 않음"은 "위험하지 않음"이 아니다. 화면에는 **"자료에서 확인되지 않음 — 담당자 확인 필요"**로 표시한다.

## 3. 대상 고객과 요구사항 기준 (D7)

가상 회사는 두지 않는다. 대신 개발 기준이 되는 세 가지를 만든다.

| 산출물 | 내용 | 작성 시점 |
|---|---|---|
| **대상 고객 프로필** | 화학물질·가스를 취급하는 중견 제조 기업 (업종은 O1에서 확정). 규모, 법적 의무, 주로 취급하는 물질과 위험 작업, IT 환경(폐쇄망, 사내 계정 시스템) | 준비 단계 |
| **요구사항 명세** | 기능·비기능 요구사항 목록과 각 항목의 검수 기준. 마일스톤 완료 판정의 기준이 됨 | 준비 단계 |
| **테스트 데이터** | 테스트용 조직·사용자·그룹(LDAP/SSO 시험용), 샘플 사내 문서(작업표준서·사고 보고서 등) | 핵심 3단계 직전 |

작성 원칙:
- 법적 의무, 업종 통계, 설비 기준처럼 **확인 가능한 사실에는 출처를 단다.** 폐쇄망 운영, 작업허가서 제도처럼 업계에서 흔한 방식은 "일반 관행"으로 표시한다.
- 요구사항은 특정 회사의 사정이 아니라 **해당 업종 기업이 일반적으로 요구할 만한 수준**으로 쓴다. 가능하면 업계 종사자나 안전 분야 전문가에게 현실성을 검토받는다.
- 샘플 사내 문서는 KOSHA 지침과 공개 양식을 참고해 작성하고, 모든 문서에 "테스트용 샘플"이라고 표시한다.

## 4. 설계 원칙

### 온프레미스 우선 원칙

1. **처음부터 설치 형태로 개발한다.** 개발 환경도 Docker Compose로 구성하고, 인터넷을 차단한 상태로 동작을 시험한다.
2. **외부 의존을 한 곳에 모은다.** 외부 API(MSDS, 법령), 메일 발송, 모델 호출은 지정된 모듈에서만 하고, 각각 오프라인 대체 경로를 둔다.
3. **직접 설치할 수 있는 구성 요소만 쓴다.** PostgreSQL+pgvector, 자체 인증. 클라우드 전용 관리형 서비스는 쓰지 않는다.
4. **임베딩은 처음부터 로컬 모델을 쓴다.** 나중에 다시 색인할 필요가 없다.
5. **로컬 LLM 품질을 일찍 확인한다.** 에이전트를 만든 직후 로컬 모델로 같은 평가를 돌린다.

### 공개 웹 전환 대비 원칙

6. **모든 데이터에 조직(tenant) 구분을 넣는다.** 기업 내 공장·부서 분리에도 필요하고, 공개 웹에서는 회사별 분리로 쓰인다.
7. **인증은 교체 가능한 구조로 만든다.** 관리자 발급 계정을 먼저 만들고, LDAP·SSO·회원가입을 같은 인터페이스로 추가할 수 있게 한다.
8. **설정으로 배포 형태를 바꾼다.** 온프레미스/공개 웹 차이는 설정값과 배포 파일로만 둔다.

### 안전 정보 원칙 (기획서 5.3 유지)

9. 모든 점검 항목에 출처(사례 번호, 조문, 지침 번호, 문서 ID)를 표기한다.
10. 근거가 없으면 "확인되지 않음"으로 답한다.
11. 확정적 안전 지시가 아니라 점검 초안과 참고 자료를 제공한다. 최종 판단은 사업장 안전 담당자가 한다.

## 9. 개발 방식과 하네스 설계 (학습형, D5)

### 한 기능을 만드는 흐름

1. **설명:** 만들 기능, 필요한 이유, 관련 개념
2. **코드 전달:** 항상 **완성된 전체 코드**를 보낸다. 파일 하나 또는 함수 몇 개 단위로, 블록별 설명과 함께 (D9)
3. **직접 작성:** 개발자가 이해하며 붙여 넣고, 모르는 부분은 질문
4. **실행·확인:** 실행 명령과 기대 결과 안내. 결과·오류를 가져오면 함께 분석
5. **리뷰:** 개발자가 작성한 코드를 Claude가 읽고 피드백 (수정은 개발자가 직접)
6. **이해 확인 (완료 조건, D9):** 기능의 핵심 개념 2~3개를 개발자가 자기 말로 설명하고, Claude가 빠지거나 틀린 부분을 짚는다. 테스트 통과 + 이해 확인까지 해야 기능 완료
7. **정리:** 배운 개념, 아직 헷갈리는 것, 복습할 것을 학습 기록에 남긴다

개발자는 사용 기술을 AI 도움으로 다뤄 본 경험이 있다. 따라서 이 방식의 목표는 기술을 처음 배우는 것이 아니라 **"왜 이렇게 짜는지 설명할 수 있는 수준"으로 이해하는 것**이다. 오류가 나면 답을 바로 주지 않고 "어디를 볼지 → 원인 → 해결 코드" 순서로 단계적으로 안내한다.

### 하네스 구성 (D14, 준비 4주차에 구축)

AGENTS.md 계층 구조(상시 규칙 → 실행 계획 → 반복 작업 자동화 → 검증 → 출시 체크리스트)를 따르고, 학습형 방식을 위해 **차단 장치(훅)**와 **학습 기록**을 더한다. 처음에는 최소 구성으로 시작하고 필요할 때 늘린다.

```
industrial_safety/
├── AGENTS.md            공통 상시 규칙 (도구 무관 표준)
├── CLAUDE.md            AGENTS.md를 불러오는 한 줄 (Claude Code용)
├── CHECKLIST.md         마일스톤별 출시(설치) 전 확인 목록
├── README.md            설치·실행 방법 (묶음 A에서 개발자가 작성)
├── docs/
│   ├── PLAN.md          전체 계획 (이 문서)
│   ├── progress.md      작업 목록 진행 상태
│   └── learning-log.md  학습 기록
├── .claude/
│   ├── settings.json    차단 장치(훅)
│   └── skills/          스킬
├── evals/               평가 시험지와 채점 (정답은 사람만 수정)
├── backend/AGENTS.md    백엔드 전용 규칙 (폴더가 생길 때)
└── frontend/AGENTS.md   프론트엔드 전용 규칙 (폴더가 생길 때)
```

| 계층 | 구성 | 역할 |
|---|---|---|
| 상시 규칙 | AGENTS.md (+ CLAUDE.md), 폴더별 AGENTS.md | Claude의 역할을 **설명자·리뷰어**로 정의. 앱 코드는 대화로만 전달. 폴더별 코드 규칙 |
| 실행 계획 | docs/PLAN.md, docs/progress.md | 전체 계획, 작업별 진행 상태. 작업마다 `/lesson`이 실행 순서를 안내 |
| 차단 장치 | .claude/settings.json 훅 | Claude가 backend/·frontend/ 등 앱 코드 폴더에 쓰기 차단, evals 정답·.env 접근 차단 → 학습형 방식을 기계적으로 보장 |
| 반복 작업 (학습 절차) | `/lesson` 작업 설명 + 전체 코드 · `/debug` 오류 분석(힌트 → 원인 → 해결 코드) · `/review` 코드 리뷰 · `/done` 테스트 확인 + 이해 확인 + 완료 표시 · `/wrap` 학습 기록 정리 | 준비 4주차에 구축 |
| 반복 작업 (작업 절차) | `eval-run` (묶음 D), `release-readiness` (묶음 F), `source-intake` (2단계) | **같은 일을 두 번째 할 때** 만든다. 처음엔 직접 해 보며 순서를 익힌다 |
| 검증 | evals/, `make check` | 품질 평가, 테스트·코드 규칙 검사. `make check`는 프로젝트 코드이므로 묶음 A에서 개발자가 작성 |
| 출시 체크리스트 | CHECKLIST.md | 인터넷 차단 동작, 새 서버 설치, 출처 표기율, 비밀 정보 미포함 등 |
| 학습 기록 | docs/learning-log.md | 배운 개념, 헷갈리는 것, 복습할 것. 세션 시작 시 progress와 함께 불러옴 |
| 나중에 추가 | 서브에이전트 | 필요할 때 추가 (예: 묶음 E에서 안전 정보 검토자) |
